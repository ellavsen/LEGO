## 1. Executive Summary

**Что это.** BrickIndex — инструмент коллекционера LEGO Technic: фото детали → идентификация (`part_num`) через retrieval (DINOv3 + FAISS по рендерам LDraw) → цвет (LAB + ограничение по `elements`) → атрибуты (отверстия/оси/форма, собственный слой) → локальная коллекция и офлайн-параметрический поиск на Android. Продуктовая ниша обоснована в LEGO.md §1: «инвентарь + параметрический поиск по геометрии + цвет» не закрыта конкурентами (Brickit/Brickognize).

**Вердикт: крепкий технический прототип «точного режима», готовность ядра подтверждена измерениями; до надёжного личного MVP — 1–2 итерации (~1–2 недели вечерней работы). Публичный запуск сейчас не планировать.**

**Что действительно работает (проверено вживую):**
- БД: 63 585 деталей, 275 цветов, 112 558 elements, 96 416 картинок; `verify_import.py` — все проверки пройдены.
- Ядро retrieval на **98 реальных фото**: Recall@5 = **92.9%** (цель ≥90% достигнута), Recall@1 = **48.0%** (цель ≥75% не достигнута — осознанный размен на top-5 UX с подтверждением). Замер воспроизведён аудитом 1:1.
- Цвет на 42 реальных фото: top-1 **67%**, top-3 **86%** (ограничение по `elements` даёт 13× против 5% без него).
- Атрибуты: **153/153** полей эталона из 30 деталей совпали.
- Сервер: `/health`, `/identify` (0.9 c, верный top-1 на тестовом фото), `/segment` (10/10 кропов на раскладке) — поднят и проверен вживую.
- Android: `assembleDebug` собирается за 29 c (19.2 МБ APK), клиент-серверный контракт совпадает, офлайн-каталог `catalog.db` (964 детали) сверен со схемой Room 1:1.

**Главные слабости:** (1) ключевой пользовательский сценарий ни разу не пройден на устройстве — только серверная приёмка; (2) набор P1-дефектов в клиенте (очередь `/confirm` с дублями и тихими потерями, «проверьте цвет» без возможности исправить, подсказка «одна-несколько деталей» при неиспользуемой `/segment`); (3) нет системы контроля версий и резервного копирования — 5.5 ГБ проекта (3.3 ГБ рендеров ≈ 9+ часов генерации) не защищены ничем; (4) не реализован «отказ от ответа» (`confidence`/`unknown`), прямо предписанный Спринтом 4.

**Главные риски:** ложные записи в коллекцию без сигнала неуверенности; потеря коллекции/данных калибровки из-за отсутствия бэкапов; расхождение документации с кодом (venv-команды сломаны, боевая конфигурация описана противоречиво).

**Что мешает запуску:** не блокирует ничего фундаментального — ядро работает. Мешают: P1-дефекты клиента, отсутствие прогона на телефоне, отсутствие git/бэкапов, недосказанность UX (цвет, «не уверена», онбординг).

**Рекомендуемый следующий шаг:** git init + `.gitignore` + коммит, затем прогон чек-листа на телефоне (§8) и фиксы P1 (§7, этапы 0–3).

## 3. Сильные стороны

1. **Честная валидация ядра на реальных фото** ✅. Recall меряется на 98 реальных фотографиях Rebrickable (рендеры из валидации исключены — ПАТЧ п.3), на полном индексе 623 деталей, а не на «удобных» 100. Метрики воспроизводятся: аудит повторил `eval_real.py` и получил те же 48.0 / 92.9%. Это редкая дисциплина — именно она делает текущие цифры заслуживающими доверия.

2. **Retrieval-first архитектура с измеримо работающим re-ranking** ✅. Multi-view индекс (24 ракурса/деталь, IndexFlatIP), агрегация max, геометрический re-ranking по габаритам из LDraw (`retrieval.py:98-134`). Живая проверка: для фото 32524 без re-ranking top-1 = 40490 (неверно), с re-ranking — 32524 (верно). Архитектура дешёва в поддержке новинок (добавить вектор, не переобучать) — обоснована в LEGO.md §2.2.

3. **Атрибутный слой — «оборонимый ров», сделанный правильно** ✅. Три источника с явными приоритетами (имя → LDraw-геометрия → курирование), курированные строки защищены от перезаписи (`fill_attributes.py:38`, `source != 'curated'`), семантика LDraw-примитивов откалибрована и задокументирована (`ldraw_geom.py:7-13`), проверка 153/153 на ручном эталоне. Это главное конкурентное преимущество продукта, и оно реализовано не «для галочки».

4. **Идемпотентный атомарный импорт каталога** ✅. Temp-таблица + COPY + `ON CONFLICT DO UPDATE`, ни одного DELETE (исчезнувшие строки не удаляются — правильное решение для каталога, на который ссылается коллекция), вся работа в одной транзакции (`import_catalog.py:65-129`). Подтверждено журналом `import_log` (12 строк = 2 прогона × 6 таблиц).

5. **Цвет как первоклассный признак с продуктовой честностью** ✅. Ограничение по `elements(part_num)` (главный буст, 13×), флаг `color_needs_confirmation` для «трудных пар», осознанный вес L=0.4. Метрики на 42 фото воспроизведены (67/86/5%).

6. **Офлайн-каталог на устройстве с гарантией согласованности схем** ✅. `assets/catalog.db` генерируется из Postgres (`export_catalog_snapshot.py`), схема сверена с Room 1:1 (включая NOT NULL-конверсии `coalesce(has_axle,false)`, `int(t)`); в снапшоте 0 JOIN-сирот. Поиск по атрибутам работает без сервера и мгновенно — ровно как задумано в §6.2.

7. **Качественная инженерная документация** ✅. LEGO.md (ТЗ + исследование + спринты) и CLAUDE.md (боевые факты: ловушки libomp/JDK 21/ImportLDraw, метрики, команды) — редкий уровень «передачи знаний самому себе». Документация местами разошлась с кодом (§4), но сам подход стоит сохранить.

**AND-01** — доказательства: `vm.flushPending()` стоит в `setContent`-лямбде; композиция пересобирается при каждой смене вкладки (backStack — state). Два конкурентных цикла читают одну и ту же pending-строку до `dequeue` → дублирующие INSERT в `confirmations`. Последствия: загрязнение few-shot-набора дублями (обучающая выборка калибровки). Исправление: `LaunchedEffect(Unit)` + одиночный Job/Mutex. Проверка: лог `/confirm` при переключении вкладок — ровно один POST на строку.

**AND-02** — `if (f.exists()) { api.confirm(...) }; user.dequeue(p.id)` — при очистке cacheDir строка удаляется без отправки (few-shot-сэмпл потерян молча); `catch { break }` — устойчивая ошибка первой записи блокирует всю очередь. Исправление: хранить фото очереди в `filesDir/confirm_queue` (не cacheDir) + per-item обработка ошибок (пропуск проблемной строки с пометкой, не блокировка очереди). Проверка: очистить cacheDir → перезапуск → строка не потеряна; испортить одну запись → остальные уходят.

**AND-04** — цвет — «первоклассный признак» продукта (LEGO.md §9), а top-1 цвета верен в 67% случаев; при флаге «проверьте цвет» пользователь не может выбрать из `color_alternatives` (клиент их игнорирует) и не может исправить позже. ~1/3 строк коллекции получит неверный цвет навсегда. Исправление: пикер цвета в диалоге подтверждения (top-3 альтернативы) + редактирование строки коллекции (цвет/qty/location). Проверка: сценарий «цвет неверный → исправить в диалоге/коллекции».

**AND-05** — подсказка — единственный онбординг экрана скана; следуя ей, пользователь гарантированно получает плохой результат (в `/identify` эмбеддинг считается по всему кадру, `app.py:70-71`). Исправление (минимальное): текст «Одна деталь на контрастном фоне…» до реализации связки `/segment` → кропы → `/identify` по каждому кропу. Проверка: фото с двумя деталями → после фикса текста сценарий не провоцируется; после реализации — top-K по каждой детали.

3. **Переезд на SAM 3 / DINOv3-тонкости / YOLO26** — текущее качество ядра измерено и достаточно для top-5 UX; смена моделей потребует пересборки индекса (~9.5 ч) и полного перезамера — без измеримой причины это чистый риск.
4. **Публичная инфраструктура** (HTTPS, авторизация, Docker, автоскейл, мониторинг, платежи) — до решения открытого вопроса «личный инструмент или публичный продукт» (Прил. Б.3) это преждевременные траты.
5. **«Скан кучи», «чего не хватает для набора», «умные замены», on-device эмбеддер, iOS** — явно отложены ТЗ в Фазу 2; каждая из них удваивает риск, не добавляя проверенной ценности.
6. **Массовый рефакторинг/смена стека** — архитектура работает и задокументирована; переписывание не добавляет ни одной проверенной метрики.
7. **Аналитика/телеметрия** — для личного инструмента не нужна; для публичного потребует privacy-дизайна (фото пользователей).
8. **Расширение каталога за пределы Technic** — атрибутный ров строится на Technic-фокусе; расширение до подтверждения ценности размоет усилия курирования.

## 10. Критерии готовности к запуску (Definition of Done MVP)

Личный MVP считается готовым, когда **все** пункты выполнены:

1. Основной сценарий «снял → подтвердил → нашёл по фильтрам» проходит на устройстве без подсказок разработчика (чек-лист §8 пп. 1–2 ✅).
2. Блокирующие дефекты закрыты: AND-01…AND-05, SRV-01, AND-03, OPS-01, OPS-02 (регресс-проверки пройдены).
3. `/identify` помечает «не уверена / нет в каталоге» (порог по негативам) и такие кандидаты нельзя записать в коллекцию.
4. Цвет можно исправить при подтверждении и позже в коллекции.
5. Метрики ядра не ухудшились после изменений: R@5 ≥ 90% на 98 реальных фото (перезамер `eval_real.py`).
6. Очередь `/confirm` не теряет и не дублирует записи (проверка: 20+ офлайн-подтверждений, очистка кэша).
7. `git status` чист; `.env` не в репозитории; токен ротирован; в логах нет секретов.
8. Инструкции запуска выполняются дословно (venv-команды работают или заменены на `python -m`).
9. Проверен сценарий восстановления: коллекция экспортирована в CSV и импортирована обратно после переустановки; `pg_dump`/restore для `confirmations`.
10. Битый файл → 400, не 500; путь из `chosen_part_num` не выходит за `confirm_crops`.

Пункты 1, 7, 8, 10 — пороговые; 5 — метрика; остальные — функциональные проверки. Ни один пункт не является «кодом хорошего качества» без измеримой проверки.

## 11. Первые пять действий

1. **`git init` + `.gitignore` + первый коммит + ротация `HF_TOKEN`** (OPS-01/OPS-02). Почему первым: каждый следующий час работы без этого рискует всем проектом (5.5 ГБ, из них рендеры — ~9.5 часов регенерации). Результат: проект неубиваем, секрет вне репозитория.
2. **Прогон чек-листа на телефоне** (§8 пп. 1–7, ~1 час). Почему вторым: все следующие фиксы приоритезируются по фактическим дефектам, а не по статике. Результат: список подтверждённых на устройстве дефектов.
3. **AND-05 + AND-04** (текст подсказки + пикер цвета/редактирование). Почему третьим: это минимальные изменения с максимальным эффектом на честность данных — подсказка больше не ведёт к мусорным записям, неверный цвет перестаёт быть необратимым.
4. **AND-01/AND-02/AND-03** (очередь подтверждений + ошибка съёмки). Почему четвёртым: few-shot-маховик — стратегический актив проекта (калибровка эмбеддера); он должен копить чистые данные с первого дня использования.
5. **SRV-01 «отказ от ответа»** (негативы → порог → `confidence`/`unknown` + блок записи в клиенте). Почему пятым: это последний P1, который делает каталог надёжным («ложная запись хуже отсутствия записи»), и он требует сбора 20 фото-негативов — его можно готовить параллельно с п. 4.

Выводы категорированы (✅/⚠️/❔/💡); противоречия между аудиторами разрешены фактическими проверками (пример: утверждение о нарушении FK цветом −1 опровергнуто — `−1 [Unknown]` существует в Postgres и в дампе).*
