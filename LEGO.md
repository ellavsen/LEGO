Одно замечание перед стартом, потому что оно меняет постановку: **retrieval-first — правильное решение, но у него есть недооценённое ограничение, которое надо заложить в архитектуру с первого дня** (см. §2.4 и §10.3). Rebrickable знает *идентичность* детали и её изображения, но НЕ хранит структурированно те параметры, по которым вы хотите искать («7 отверстий», «есть ось», «угловая»). Поэтому система = два слоя: retrieval даёт `part_num`, а отдельный **слой атрибутов** превращает `part_num` в искомые параметры. Без этого запрос «liftarm, 7 отверстий, угловая, чёрная» не выполним в принципе.

# ЧАСТЬ I. ИССЛЕДОВАНИЕ

## 1. Что уже существует (и где ниша)

Рынок распознавания LEGO в 2026-м уже не пустой — это важно понимать честно, потому что «где я лучше» определяет продукт сильнее, чем «как я это сделаю».

| Продукт | Что делает | Модель/технология | Слабые места (= ваша ниша) |
|---|---|---|---|
| **Brickit** | Массовый потребительский апп: сканирует кучу, считает детали, предлагает *что построить* + инструкции, подсвечивает деталь в куче | Собственная детекция; заявленная точность детекции ~92% (2023) | **Не различает цвет.** Требует раскладки в один слой. Пропускает перекрытые детали. Ориентирован на «что построить», а не на инвентарь/каталог. Слабо покрывает Technic и спецдетали. |
| **Brickognize** | Веб-инструмент + API: определяет *одну* деталь/минифигурку/принт по фото, даёт ссылки на BrickLink/Rebrickable | ConvNeXt-T (28M параметров), классификация | Одна деталь за раз (мульти-распознавание было в планах). Нет инвентаря, нет параметрического поиска. Это «движок», а не «продукт коллекционера». |
| **brick'em / Bricqer** | Обёртки над Brickognize API для реселлеров: инвентарь, цены, экспорт на BrickLink/eBay | Тот же Brickognize | Заточены под продажу/склад магазина, не под личную коллекцию с поиском по геометрии. |
| **Setognize, LegoSorter** | Учебные/нишевые проекты: распознавание наборов, счёт деталей | Рендер-датасеты + CNN | Не продукты, а референсы кода. |
| **BrickLink / Rebrickable (сайты)** | Гигантские каталоги, ручной поиск по категориям | БД | Поиск ручной и не «параметрический» в вашем смысле; нет распознавания вашей физической коллекции. |

**Вывод по нише.** Никто не закрывает связку, которую вы описали:

> «Умный **инвентарь личной коллекции** + **параметрический поиск по геометрии** (пины/отверстия/длина/ось/шарнир/форма) + **цвет** + фокус на **Technic**.»

Brickit — про «что построить», Brickognize — про «что это за деталь», сайты-каталоги — про ручной просмотр. Ваш продукт — про «**найти нужную деталь в физической коллекции по инженерным признакам**». Это реальная, не занятая ниша, и она особенно ценна именно для Technic-коллекционера, потому что Technic — это как раз детали, которые различаются по числу отверстий, наличию оси и форме, а не по цвету.

## 2. Ключевое архитектурное решение: retrieval-first vs classification-first

Это центральный раздел. Вы сформулировали идею правильно; здесь я её разбираю до конца, показываю, где она сильна, где её надо усилить, и как именно строить.

### 2.1. Две постановки задачи

- **Classification-first («что это за объект?»).** Обучаем модель с N выходами-классами (N = число типов деталей). Модель на выходе даёт вероятность по каждому классу. Так работает Brickognize (ConvNeXt) и большинство учебных проектов.
- **Retrieval-first («какая из известных деталей перед нами?»).** Не классифицируем, а **сравниваем**. Кодируем фото детали в вектор-эмбеддинг, и ищем ближайший вектор в заранее построенном индексе всех деталей библиотеки (Rebrickable). Ответ — не «класс», а «ближайший сосед» + расстояние.

### 2.2. Почему retrieval-first для LEGO объективно лучше

1. **Открытый набор классов без переобучения.** В каталоге LEGO десятки тысяч деталей, и он растёт каждый месяц. У классификатора добавление нового класса = переобучение/дообучение и риск деградации. У retrieval добавление детали = **посчитать один эмбеддинг и добавить в индекс**. Ноль переобучения. Для проекта одного человека это решающее преимущество по стоимости поддержки.

2. **Задача становится проще геометрически.** Классификатор должен провести разделяющие границы между всеми классами одновременно (очень сложное пространство при 50k классов, многие из которых почти неотличимы). Retrieval требует лишь, чтобы **похожие изображения были рядом** в пространстве эмбеддингов — а это ровно то, чему self-supervised модели (DINOv3) обучены by design.

3. **Top-K вместо top-1, и это фича, а не баг.** Похожие детали (liftarm 1×5 vs 1×7, разные пины) retrieval честно вернёт как кластер кандидатов с расстояниями. Пользователю показываем top-5 с картинками — он подтверждает за секунду. Для коллекционера это лучше, чем ложная уверенность классификатора в top-1.

4. **Синергия с цветом и атрибутами.** Как только известен `part_num`, мы знаем (из Rebrickable), в каких цветах эта деталь вообще выпускалась → определение цвета превращается из «угадать из 200 цветов» в «выбрать из 3–5 возможных». То же с атрибутами: идентичность → все параметры из слоя атрибутов.

5. **«Холодный старт» решается синтетикой.** Индекс можно построить целиком из **рендеров** (LDraw → Blender), не имея ни одной реальной фотографии. День-два рендеринга — и у вас эталонная база на весь каталог.

### 2.3. Где retrieval-first слабее (и как чинить)

- **Синтетик-реалити гэп.** Эталоны — рендеры, запросы — реальные фото (блики, износ, пыль, тени). Если кодировать «в лоб», расстояния плывут. **Решение:** (а) DINOv3 сам по себе устойчив к домену; (б) few-shot дообучение эмбеддера на 20–200 реальных фото (проверено в литературе для LEGO — синтетика + few-shot реальных даёт AP50 ~91% в неконтролируемых условиях); (в) аугментации рендеров под «реальность» (случайный фон, свет, блики).
- **Очень похожие детали.** Retrieval вернёт их вместе, но не всегда правильно упорядочит top-1. **Решение:** re-ranking (см. §8.4) + подтверждение пользователем + использование атрибутного слоя как фильтра («это точно liftarm, а не beam»).
- **Ориентация/ракурс.** Одна деталь с разных ракурсов даёт очень разные картинки. **Решение:** в индекс кладём **не один, а много** эмбеддингов на деталь (multi-view: рендеры с 12–36 ракурсов), поиск — по всем; часто это называют «мульти-вью retrieval».

### 2.4. Критическое уточнение к вашей постановке

> Вы написали: «сопоставлять с полной библиотекой Rebrickable, **где уже известны все геометрические параметры**».

Здесь важная поправка, которая экономит месяцы: **Rebrickable НЕ хранит геометрические параметры в структурированном виде.** Он хранит: `part_num`, имя, категорию, внешние ID (BrickLink/LDraw/BrickOwl), связь с цветами и наборами, и картинки. Полей вида «отверстий = 7 / есть ось = да / форма = угловая» там **нет**.

Значит, retrieval решает только задачу **идентичности** (фото → `part_num`). А ваш параметрический поиск требует **отдельного слоя атрибутов**, который надо построить самому. Хорошая новость: это делается и это самая «оборонимая» часть продукта (см. §10.3). Плохая — если этого не заложить в план, вы обнаружите на середине, что искать «7 отверстий» не по чему.

**Итоговая формула архитектуры:**

```
Фото → [сегментация] → кроп детали → [эмбеддинг DINOv3] → [поиск в FAISS по каталогу]
     → part_num (идентичность)
                          ↓
        [слой атрибутов: part_num → {holes, pins, length, has_axle, shape, ...}]
                          ↓
        [определение цвета, ограниченное цветами этой детали]
                          ↓
                 запись в каталог коллекции
```

## 3. Данные: откуда всё брать

### 3.1. Rebrickable — фундамент каталога

- **Бесплатные CSV-дампы** (обновляются ежедневно, «можно использовать для любых целей»): `parts.csv`, `colors.csv`, `part_categories.csv`, `elements.csv` (part×color→element_id), `part_relationships.csv`, инвентари наборов. Это ваш справочник идентичности и цветов — **скачивается целиком, работает офлайн**.
- **API v3** — real-time, но с rate-limit (≈1 req/sec), для bulk не годится. Используем точечно (проверка новинок, картинки).
- **Изображения деталей** — доступны на скачивание zip-архивами по цветам. Плюс есть внешние ID на BrickLink/LDraw.

### 3.2. LDraw — 3D-модели для рендера эталонов

LDraw — открытая библиотека 3D-моделей почти всех деталей LEGO. Через Blender (аддон ImportLDraw / современные LEGO-аддоны) можно **программно отрендерить любую деталь с любого ракурса, в любом свете, на любом фоне**. Это ваш генератор:
- эталонных изображений для индекса retrieval (multi-view);
- обучающих данных для сегментации/детекции (с идеальной разметкой масок «бесплатно»);
- источник **геометрии** для автоизвлечения атрибутов (§10.3): в LDraw-модели отверстия/оси/пины — это конкретные примитивы и субфайлы, их можно посчитать программно.

### 3.3. Готовые датасеты и код (не изобретать велосипед)

- **`360er0/awesome-lego-machine-learning`** — курируемый список всех LEGO-ML ресурсов. Начать отсюда.
- **Синтетические пайплайны рендера:** несколько открытых репозиториев (Blender + ImportLDraw) генерируют сцены с масками в формате COCO. Научная работа (Sensors, 2023) показала: **синтетика + 20 реальных фото few-shot → AP50 91.3%** в неконтролируемых условиях. Это прямое подтверждение, что подход рабочий без ручной разметки тысяч фото.
- **Готовые классификационные датасеты** (200 популярных деталей × 4000 изображений и др.) — для быстрого baseline и валидации.
- **Nature Scientific Data (2023)** — публичный датасет рендеров + реальных фото LEGO, для обучения/валидации.

### 3.4. Нужно ли размечать фото вручную?

**Почти нет** — и это ключевой выигрыш retrieval + синтетики:
- Индекс retrieval строится из рендеров → разметка не нужна вообще.
- Сегментацию берём из готовой модели (SAM 3, §4.2) — тоже без разметки.
- Ручная разметка нужна лишь для небольшого **валидационного набора реальных фото** (сотни, не тысячи) и для few-shot калибровки эмбеддера. Реалистично собрать самому за пару вечеров, фотографируя свою коллекцию.

## 4. Технологии 2026: что применять и почему

За последний год всё сместилось — актуальный стек отличается от того, что советовали в 2025-м.

### 4.1. Эмбеддер (сердце retrieval): DINOv3

- **DINOv3** (Meta, 2025) — self-supervised ViT, обучен без меток на 1.7 млрд изображений; есть **дистиллированные варианты** (ViT-S/B/L и ConvNeXt), поддержка в HuggingFace Transformers (≥4.56) и timm (≥1.0.20).
- Почему он: даёт качественные эмбеддинги, по которым k-NN-разделимость классов сильна «из коробки» → идеально под retrieval. Устойчив к домену (важно для синтетик→реалити).
- Практика: **ViT-S/B дистиллят** для баланса скорость/качество. ViT-S достаточно лёгок, чтобы при желании гонять эмбеддинг on-device; ViT-B — на сервере для максимума качества.
- Лицензия DINOv3 — специфическая (не такая пермиссивная, как у DINOv2); чекпоинты gated на HF. **Проверить условия использования для вашего кейса** (Приложение Б).
- Альтернатива/бэкап: DINOv2 (пермиссивнее) или CLIP-эмбеддинги; для fine-grained LEGO DINO-семейство обычно выигрывает у CLIP.

### 4.2. Сегментация «найти и разделить все детали»: SAM 3 / SAM 3.1

- **SAM 3** (Meta, ноябрь 2025) + **SAM 3.1** (март 2026) — умеет **promptable concept segmentation**: по текстовому промпту («lego brick») или по exemplar-примеру находит и сегментирует **все экземпляры** концепта на изображении/видео, с отдельными масками и ID. Интегрирован в Ultralytics (≥8.3.237).
- Почему это подарок для вашей задачи: шаг «разложить кучу на отдельные детали» решается **без обучения своей модели**. Промпт «lego piece» + exemplar → маски всех деталей → кропы для retrieval.
- Ограничения: SAM 3 тяжёлый (~848M параметров, детектор DETR-типа + трекер) → **серверный** инференс, не on-device. Плохо с сильными перекрытиями и очень мелкими деталями (общая беда всех моделей на плотной куче).
- Для on-device/лёгкого варианта — MobileSAM/FastSAM как фолбэк худшего качества.

### 4.3. Детектор (альтернатива/дополнение к SAM): YOLO26 или RF-DETR

- **YOLO26** (Ultralytics, январь 2026) — новейший, NMS-free, заточен под edge/低-power, мультизадачный (detection/segmentation/pose/obb/cls), ~43% быстрее на CPU, чем YOLO11n. Хорош, если хотим **свой** быстрый детектор «есть деталь / нет» + грубый bbox, в т.ч. on-device.
- **RF-DETR** — по обзорам 2026-го лучший для **кастомного дообучения** (DINOv2-претрейн → адаптируется к новому домену с меньшим числом данных). Кандидат, если будете обучать детектор под свою съёмочную обстановку.
- Роли: **SAM 3** — качественная сегментация масок (сервер); **YOLO26** — быстрый предварительный детектор/on-device. Можно комбинировать (YOLO26 находит регионы, SAM 3 уточняет маски).

### 4.4. Индекс поиска: FAISS

- **FAISS** (Meta) — векторный индекс для ANN-поиска. Каталог LEGO (десятки тысяч деталей × десятки ракурсов) = миллионы векторов максимум — для FAISS это мало, поиск — миллисекунды. Нормализуем эмбеддинги, L2/cosine, `IndexFlatIP` на старте (точный), позже `IVF/HNSW` при росте.

### 4.5. Чего НЕ брать (и почему)

- **Обучать классификатор на 50k классов с нуля** — дорого, хрупко, требует переобучения на каждую новинку. Retrieval снимает это.
- **Detectron2 / чистый Mask R-CNN своими руками** — устарело относительно SAM 3 для сегментации; больше кода и разметки ради худшего результата.
- **Тяжёлый full on-device inference всего пайплайна на старте** — SAM 3 и DINOv3-B на телефоне не потянуть комфортно. On-device — цель второй фазы (лёгкие дистилляты), не MVP.
- **OpenCV как «распознаватель»** — OpenCV полезен для препроцессинга (баланс белого, кропы, морфология), но не для распознавания деталей. Вспомогательный инструмент, не ядро.

## 5. Оценка сложности

По честной инженерной шкале (1 — тривиально, 10 — фронтир исследований):

| Подзадача | Сложность | Комментарий |
|---|---|---|
| Каталог + параметрический поиск (БД, фильтры) | **3/10** | Стандартная разработка. Основная работа — курирование атрибутов. |
| Определение цвета (после сегментации) | **4/10** | Решаемо (LAB + баланс белого + ограничение по цветам детали). Свет — главный враг. |
| Retrieval идентичности одной чистой детали | **5/10** | DINOv3 + FAISS + синтетика. Рабочее решение с известными компонентами. |
| **Слой атрибутов (holes/axle/shape...)** | **6/10** | Не по алгоритму, а по объёму курирования/парсинга геометрии. Самое «оборонимое». |
| Сегментация кучи 100–300 деталей с перекрытиями | **7/10** | SAM 3 помогает, но плотные перекрытия — принципиально тяжело. |
| **Точный подсчёт + цвет + ID для всех деталей в плотной куче за один кадр** | **8–9/10** | Это фронтир. Даже Brickit здесь теряет перекрытые детали и не даёт цвет. Не обещать себе 100%. |

**Главный вывод по сложности:** «одна деталь / несколько разложенных деталей → точный ID + цвет + атрибуты» — **реалистично и качественно**. «Плотная куча 300 деталей за один кадр с идеальным счётом» — **не решается на 100% ничем в мире**; это надо принять как продуктовое ограничение, а не как задачу, которую вы дожмёте.

Отсюда — важное продуктовое следствие в §12.

### 6.2. Локально vs сервер vs облако — решение

- **MVP: тонкий клиент + сервер.** Тяжёлые модели (SAM 3, DINOv3-B) — на сервере. Клиент отправляет кроп/фото, получает JSON с ID/цветом/атрибутами. Причина: on-device этих моделей на старте не даст качества и утопит сроки.
- **Каталог и поиск — локально.** БД коллекции и каталог деталей живут на устройстве (SQLite/Room) → поиск и просмотр работают **офлайн и мгновенно**. Синхронизация с сервером — для распознавания и обновлений каталога.
- **Фаза 2: гибрид.** Лёгкий эмбеддер ViT-S on-device → офлайн-ID разложенных деталей без сервера; сервер — только для сложных сцен и обновления индекса.
- **Облако:** одна недорогая GPU-инстанс (или CPU для DINOv3-S) под инференс. Для личного проекта — включать по запросу/держать маленький сервер. Публичный продукт — автоскейл.

### 6.3. Синхронизация

- Каталог/индекс: версионируются; клиент подтягивает дельты (новые детали → новые строки + новые векторы). Retrieval-архитектура делает это дёшево (добавить вектор, а не переобучать).
- Коллекция пользователя: локальный источник правды + опциональный бэкап в облако (позже — мультиустройство).

## 7. Pipeline распознавания (полный)

```
1. ЗАХВАТ
   Фото (одна деталь / раскладка / куча) + подсказки UX (ровный свет, контрастный фон).

2. ПРЕПРОЦЕССИНГ (клиент/сервер)
   Баланс белого по эталону (лист/карточка известного цвета в кадре — сильно повышает точность цвета),
   коррекция экспозиции, ресайз.

3. СЕГМЕНТАЦИЯ (сервер, SAM 3.1)
   Промпт-концепт «lego piece» (+ exemplar) → маски всех деталей + bbox + instance ID.
   → Список кропов, по одному на деталь.

4. ПО КАЖДОЙ ДЕТАЛИ:
   4a. ЭМБЕДДИНГ (DINOv3-B) → вектор v.
   4b. RETRIEVAL (FAISS) → top-K (part_num, distance).
   4c. RE-RANKING (см. §8.4) → уточнённый порядок кандидатов.
   4d. ЦВЕТ: сэмпл пикселей внутри маски → LAB → ближайший цвет
       ИЗ МНОЖЕСТВА цветов, в которых существует top-1 part (Rebrickable elements).
   4e. АТРИБУТЫ: part_num → слой атрибутов (holes, pins, length, axle, hinge, shape...).

5. АГРЕГАЦИЯ
   Подсчёт одинаковых (part_num, color) → количества.
   Уверенность: distance top-1 vs top-2 → флаг «нужно подтверждение».

6. ПОДТВЕРЖДЕНИЕ (UX)
   Спорные детали показываем с top-3 картинками; пользователь тапает верную.
   → Верные подтверждения складываем в «few-shot»-набор для дообучения эмбеддера.

7. СОХРАНЕНИЕ
   Запись/инкремент в каталоге коллекции (part_num, color, qty, дата, фото-превью).
```

## 8. Retrieval-модуль в деталях (ядро продукта)

### 8.1. Построение индекса (офлайн)

1. Для каждой детали каталога взять LDraw-модель.
2. Отрендерить **multi-view**: 12–36 ракурсов (сфера вокруг детали), варьируя свет/фон/материал; часть рендеров — «реалистичные» (PBR-фон, блики) для сокращения домен-гэпа.
3. Прогнать через DINOv3 → эмбеддинги. В индекс кладём **все ракурсы** (несколько векторов на `part_num`), либо усреднённый прототип + несколько «якорей».
4. Собрать FAISS-индекс (нормализация, cosine/IP).

Размер: даже 50k деталей × 24 ракурса = 1.2M векторов × (384–768 float) — считанные гигабайты, поиск — миллисекунды.

### 8.2. Запрос

Кроп реальной детали → DINOv3 → вектор → FAISS top-K (K≈20) → сгруппировать по `part_num`, агрегировать расстояния по ракурсам (min или soft-vote) → кандидаты.

### 8.3. Калибровка под реальность (few-shot)

- Стартуем на чистой синтетике.
- Собираем 20–200 реальных фото своих деталей (с известными `part_num`).
- Лёгкое дообучение проекционной головы поверх замороженного DINOv3 (metric learning: triplet/ArcFace) — подтягивает реальные фото к своим рендерам. Литература по LEGO подтверждает: синтетика + few-shot реальных резко закрывает домен-гэп.

### 8.4. Re-ranking (борьба с «почти одинаковыми»)

Когда top-1 и top-2 близки по расстоянию:
- **Фильтр атрибутами:** если пользователь заранее в UI сказал «это Technic beam» — отсечь кандидатов другой категории.
- **Геометрическая проверка:** сравнить пропорции bbox/маски запроса с известными габаритами кандидатов (габариты берём из LDraw).
- **Цвет как слабый сигнал:** если top-1 не существует в наблюдаемом цвете, а top-2 существует — поднять top-2.
- **VLM-верификатор (опция, дорого):** мультимодальная модель отвечает «это `part_num` A или B?» на паре кроп+эталон. Только для спорных ≤5%.

### 8.5. Метрики качества

- **Recall@1 / Recall@5** идентичности на валид-наборе реальных фото (цель MVP: Recall@5 ≥ 90% для одиночных чистых деталей; Recall@1 ≥ 75%).
- **Точность цвета** (доля верных цветов среди верно опознанных деталей).
- **Coverage кучи** (доля физически присутствующих деталей, которые вообще были найдены сегментацией) — отдельная и честно низкая на плотных кучах.

## 9. Определение цвета

- После сегментации сэмплируем пиксели **внутри** маски (не края — там тени/блики).
- Переводим в **LAB** (перцептивно однородное пространство), берём медиану/моду.
- **Баланс белого обязателен:** попросить в кадре эталон (белая/серая карточка) → нормировать. Без этого цвет «плывёт» от освещения. Это главный источник ошибок цвета — заложить в UX.
- Классификация: ближайший цвет из `colors.csv` (у Rebrickable есть HEX каждого офиц. цвета), **ограниченный** множеством цветов, в которых реально существует опознанная деталь (`elements`). Ограничение поднимает точность драматически.
- Различение трудных пар (trans-clear vs white, разные оттенки серого) — выносим в «нужно подтверждение».


### 10.3. Слой атрибутов — «оборонимый ров» продукта

Это то, чего нет у конкурентов и что делает возможным ваш параметрический поиск. Хранит **производные** параметры на `part_num`:

```
part_attributes(
  part_num PK FK,
  type ENUM(beam, axle, connector, panel, liftarm, gear, pin, brick, plate, ...),
  length_studs, width_studs, height,          -- габариты (из LDraw/BrickLink)
  hole_count INT,                              -- число круглых отверстий
  axle_hole_count INT,                         -- число крестовых (осевых) отверстий
  pin_count INT,
  has_axle BOOL, has_hinge BOOL, has_ball_joint BOOL, has_gear_teeth BOOL,
  shape ENUM(straight, angular, bent, curved, T, L, ...),
  angle_deg,                                   -- для угловых
  connection_types JSONB,                      -- {pin_hole, axle_hole, stud, tube...}
  source ENUM(curated, ldraw_derived, bricklink, manual)
)
```

**Как заполнять (по возрастанию усилий/качества):**
1. **Парсинг имён и категорий** Rebrickable/BrickLink — многие Technic-детали кодируют параметры в имени («Technic Beam 1×7», «Liftarm 1×3 Thin»). Регэкспы дадут 60–80% на Technic.
2. **Авто-извлечение из LDraw-геометрии** — отверстия/оси/пины в LDraw это конкретные примитивы/субфайлы (напр., осевые отверстия и штырьевые отверстия — узнаваемые компоненты). Парсер LDraw → счётчики. Это самый ценный и уникальный источник.
3. **Ручное курирование Technic-подмножества** — Technic-деталей в активном каталоге порядка тысяч, а тех, что реально встречаются у коллекционера — сотни. Их можно докурировать руками за разумное время; именно они дают ваш «магический» поиск.

**Стратегическое замечание:** начинайте атрибутный слой **с Technic-подмножества**. Оно (а) ваш личный фокус, (б) конечно и управляемо, (в) именно там параметрический поиск максимально ценен и именно там конкуренты слабы.

### 10.4. Быстрый поиск

- Индексы БД на `type`, `hole_count`, `has_axle`, `color_id`, `shape`.
- Полнотекст по именам.
- Составные фильтры → простые SQL-WHERE (не нужен ML для поиска по каталогу — только для распознавания).

## 11. Поиск и фильтры

**Базовые фильтры (MVP):** тип детали, длина (в стадах/отверстиях), число отверстий, число осевых отверстий, число пинов, наличие оси/шарнира, форма (прямая/угловая), угол, цвет, категория.

**Комбинированный запрос** (ваш пример) должен работать так:
```
type = liftarm AND hole_count = 7 AND shape = angular AND color = black
→ мгновенный SQL по part_attributes ⋈ collection
→ карточка детали + «у вас 4 шт., локация: ящик B»
```

**Дополнительно, чего захочет коллекционер (по опыту сообщества):**
- «Есть ли у меня деталь X?» → поиск по каталогу с ответом «да, N шт.» + локация.
- «Каких деталей не хватает для набора Y?» → сверка коллекции с инвентарём набора Rebrickable (у них есть инвентари наборов) → список недостающих + ссылки BrickLink.
- «Что я могу построить?» → пересечение коллекции с MOC/наборами (как Brickit, но с учётом **цвета** — то, чего Brickit не умеет).
- Теги локаций/ящиков и «где лежит эта деталь».
- Стоимость коллекции (цены BrickLink) — интересно, но зависит от их API/условий.
- Экспорт/импорт в форматах BrickLink/Rebrickable (XML/CSV) — важно для интеграции в экосистему.
- Список «замен»: «нет 1×7, но есть 1×5 + 1×3» (для Technic особенно полезно).

## 12. UX-стратегия: два режима захвата (важное продуктовое решение)

Из §5 следует: не делайте единственным флоу «сфотографируй кучу 300 деталей». Сделайте **два режима**, честных к возможностям технологии:

1. **Точный режим «Идентифицировать и добавить»** (ядро качества).
   Одна или несколько разложенных деталей на контрастном фоне → высокая точность ID + цвет + атрибуты. Это то, что работает *хорошо* и отличает вас как инструмент коллекционера-каталогизатора. Аналог Brickognize по точности, но с инвентарём и атрибутами.

2. **Быстрый режим «Скан кучи»** (охват, но lossy).
   Куча в один слой → SAM 3 находит что может → массовое пополнение с пометкой «черновик, требует проверки». Честно показываем «найдено ~N из видимых», не притворяемся, что поймали всё. Аналог Brickit, но с цветом и с последующим уточнением.

Такое разделение снимает главный репутационный риск (обещать «сфоткай 300 деталей идеально» и не выполнить) и при этом закрывает оба пользовательских сценария.

## 13. Стек технологий (2026) с обоснованием

**Android-клиент**
- **Kotlin + Jetpack Compose** — стандарт 2026, декларативный UI, быстро.
- **CameraX** — захват, подсказки по кадру.
- **Room/SQLite** — локальный каталог и коллекция, офлайн-поиск.
- **(Фаза 2) ONNX Runtime / LiteRT** — on-device ViT-S эмбеддер.

**Backend / инференс**
- **Python + FastAPI** — быстрый асинхронный API, родная среда для ML.
- **PyTorch** — базовый фреймворк для DINOv3/SAM 3.
- **Ultralytics** (≥8.3.237) — единый интерфейс к SAM 3 и YOLO26.
- **FAISS** — retrieval-индекс.
- **Hugging Face Transformers/timm** — загрузка DINOv3.
- **OpenCV** — препроцессинг, цвет, морфология.

**Данные**
- **PostgreSQL** (сервер, каталог+атрибуты) / **SQLite** (клиент).
- **Blender + LDraw (ImportLDraw)** — офлайн-рендер эталонов и обучающих данных.

**Инфра**
- Один GPU-инстанс под инференс (или CPU для DINOv3-S на старте). Docker. Объектное хранилище под индекс/картинки.

Почему не альтернативы: TensorFlow → экосистема ресёрча ушла в PyTorch; свой Mask R-CNN → SAM 3 лучше и без разметки; свой классификатор на 50k классов → retrieval дешевле в поддержке.

# ЧАСТЬ III. ПЛАН, ОЦЕНКА, РИСКИ

## 14. MVP: что входит, что потом

**Входит в MVP (цель — рабочий инструмент лично для вас, Technic-фокус):**
- Импорт каталога Rebrickable в БД.
- Слой атрибутов для **Technic-подмножества** (авто-парсинг имён + ручное докурирование ключевых деталей).
- Retrieval-ID **одной/нескольких разложенных деталей** (точный режим), сервер.
- Определение цвета с балансом белого.
- Локальный каталог коллекции + добавление детали по фото.
- **Параметрический поиск** по атрибутам (ваш главный сценарий).
- Подтверждение спорных top-K пользователем.

**Откладываем (Фаза 2+):**
- Скан плотной кучи 100–300 деталей (быстрый режим).
- On-device офлайн-распознавание.
- «Что построить с учётом цвета», недостающие детали для набора.
- Мультиустройство/облачный бэкап, соц-функции, монетизация.
- iOS.

**Принцип MVP:** сначала сделать *качественно узкое* (точный ID + атрибутный поиск по Technic), а не *плохо широкое* (куча целиком).

## 15. Дорожная карта

| Этап | Цель | Результат | Время (15–20 ч/нед) |
|---|---|---|---|
| **0. Подготовка данных** | Каталог + эталоны | Rebrickable в Postgres; пайплайн Blender/LDraw рендерит multi-view; первые атрибуты Technic из имён | 3–4 нед |
| **1. Retrieval-ядро** | Фото одной детали → part_num | DINOv3-эмбеддинги, FAISS-индекс, API `/identify`; Recall@5 на своей валидации | 4–6 нед |
| **2. Цвет + атрибуты** | Обогащение ответа | Цвет (LAB+баланс белого, ограничение по part×color); атрибутный слой Technic (парсер LDraw-геометрии) | 4–6 нед |
| **3. Android MVP** | Каталог в руках | Compose-UI, Room, добавление по фото, **параметрический поиск**, подтверждение top-K | 6–8 нед |
| **4. Калибровка** | Точность под ваши условия | few-shot на 100–200 реальных фото; re-ranking; метрики | 3–4 нед |
| **5. Сегментация кучи** | Быстрый режим | SAM 3 «lego piece», массовое пополнение-черновик | 4–6 нед |
| **6. Полировка** | Юзабилити | локации, экспорт BrickLink/Rebrickable, «недостающие детали набора» | 4–6 нед |

**MVP (этапы 0–4): ~5–6 месяцев** при 15–20 ч/нед.
**Полноценная версия (0–6): ~9–12 месяцев.**
(Это агрессивнее прежней оценки 18–24 мес именно потому, что SAM 3 и DINOv3 снимают самые дорогие раньше куски, а фокус на Technic-подмножестве сужает объём курирования.)

## 16. Реалистично ли в одиночку

При ваших вводных (средний уровень кода, активное использование ИИ-ассистентов, 15–20 ч/нед) — **да, MVP реалистичен за ~5–6 месяцев**, потому что:
- Ядро собирается из **готовых** моделей (SAM 3, DINOv3, FAISS) — вы интегрируете, а не изобретаете.
- Retrieval-подход убирает самое дорогое (обучение и переобучение классификатора).
- Синтетика убирает ручную разметку.
- Android + FastAPI + Postgres — то, где ИИ-ассистенты особенно сильны.

**Самые сложные части (реалистично):**
1. **Атрибутный слой** — не алгоритмически, а по объёму курирования/парсинга LDraw. Это ваш ров, и он требует терпения.
2. **Домен-гэп синтетика→реальность** — калибровка эмбеддера, свет, блики. Итеративно.
3. **Цвет при плохом свете** — вечная борьба; смягчается UX (эталон баланса белого).
4. **Плотная куча** — не дожимается до идеала никогда; правильно ограничить ожидания (§12).

## 17. Подводные камни (о которых новичок не подозревает)

- **Rebrickable ≠ структурированная геометрия.** Главная ловушка (§2.4). Без атрибутного слоя параметрический поиск невозможен.
- **Синтетик-реалити гэп.** Модель, «идеальная» на рендерах, проседает на реальных фото. Планировать few-shot с самого начала.
- **Лицензии и товарный знак.** LEGO® — охраняемый товарный знак; сторонние продукты обязаны дисклеймить «не связано с LEGO Group» (так делают Brickit/Brickognize). Лицензия **DINOv3** и **SAM 3** — специфические, чекпоинты gated; проверить условия коммерческого использования. Данные Rebrickable — «для любых целей», но картинки/цены BrickLink имеют свои правила.
- **Перекрытия и мелочь.** На плотной куче перекрытые/мелкие детали теряются — это физика задачи, не баг.
- **Цвет ≠ пиксель.** Баланс белого, тени, полупрозрачные детали — цвет обманчив без калибровки.
- **Взрыв «почти одинаковых».** Тысячи почти неразличимых вариантов (1×5 vs 1×7, толщина liftarm) → без re-ranking и подтверждения top-1 будет ошибаться.
- **Стоимость GPU-инференса** при публичном запуске (SAM 3 тяжёлый). Для личного использования — неважно; для продукта — считать юнит-экономику.
- **Дрейф каталога.** LEGO выпускает новинки ежемесячно → нужен процесс обновления (retrieval это упрощает, но не отменяет).
- **UX раскладки.** «Разложи в один слой на контрастном фоне» — реальное требование; продумать, чтобы не бесило.

## 18. Альтернативные пути (сравнение)

| Вариант | Плюсы | Минусы | Вердикт |
|---|---|---|---|
| **A. Обернуть Brickognize API** | Быстро, точность «из коробки», мульти-распознавание в планах | Зависимость от чужого API, нет своего рва, нет атрибутного поиска, ограничения условий | Хорош для **быстрого прототипа/бенчмарка**, плохой фундамент для «своего продукта с нуля» |
| **B. Классификатор с нуля** | Понятно, top-1 | Переобучение на каждую новинку, хрупко, дорого при 50k классов | ❌ Не рекомендуется |
| **C. Дообучить готовый классификатор (ConvNeXt/YOLO26-cls)** | Проще B | Всё равно закрытый набор, переобучение | Ограниченно; ок как компонент, не как ядро |
| **D. Retrieval-first (DINOv3+FAISS) + синтетика + атрибутный слой** | Открытый набор, дёшево поддерживать, синергия с цветом/атрибутами, свой ров | Домен-гэп, нужно строить атрибуты | ✅ **Рекомендуемый — ваша интуиция верна** |
| **E. Гибрид: retrieval-ядро + Brickognize как бэкап/бенчмарк на старте** | Быстрый старт + свой long-term | Чуть больше кода | ✅ **Прагматичный путь:** прототип на A, продукт на D |

**Рекомендация:** стройте **D**, но на первых неделях используйте **Brickognize API как бенчмарк** (эталон, с которым сравнивать свою точность) и как временный фолбэк, пока свой индекс не догонит. Это снимает риск «полгода без работающего распознавания».

## 19. Финальная оценка

- **Технически реализуем:** ✅ Да, для сценария «точный ID разложенных деталей + цвет + атрибутный поиск». Компоненты зрелые (DINOv3, SAM 3, FAISS), данные доступны (Rebrickable, LDraw). Сценарий «плотная куча целиком идеально» — ⚠️ частично, это фронтир, ограничить ожидания.
- **Коммерчески интересен:** 🟡 Средне-высоко в **нише коллекционеров-каталогизаторов** (особенно Technic и реселлеры). Массовый «что построить» занят Brickit; «что за деталь» — Brickognize. **Ваш незанятый угол — инвентарь + параметрический инженерный поиск + цвет.**
- **Необычен:** ✅ Связка «параметрический поиск по геометрии Technic + распознавание своей физической коллекции + цвет» не сделана никем на хорошем уровне.
- **Перспективен:** ✅ Retrieval-архитектура дёшева в поддержке и масштабируется на новинки без переобучения; атрибутный слой — растущий ров.

**Функции, которые сделали бы его лучшим в мире приложением для коллекционеров:**
1. **Параметрический инженерный поиск по Technic** (пины/отверстия/ось/шарнир/форма/угол) — то, чего нет ни у кого. Это ваш флагман.
2. **Цвет как первоклассный признак** (Brickit его игнорирует) — точный цвет в инвентаре и в предложениях сборки.
3. **«Где эта деталь лежит»** — локации/ящики + подсветка в фото.
4. **«Чего не хватает для набора X»** — сверка коллекции с инвентарями Rebrickable + список покупки на BrickLink.
5. **Умные замены** — «нет 1×7, собери из 1×5+1×3».
6. **Экспорт/импорт в BrickLink/Rebrickable** — интеграция в экосистему.
7. **Обучение на подтверждениях** — каждое подтверждение top-K улучшает ваш эмбеддер (маховик точности).
